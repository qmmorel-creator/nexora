Audit mené selon [`AUDIT_PROMPT.md`](AUDIT_PROMPT.md), deux grilles en parallèle :
**Impeccable** (ingénierie) et **UI/UX PRO MAX** (expérience).

- Base auditée : branche `claude/quirky-fermi-urv8rp`, commit `7bfeb4d`.
- Périmètre : `apps/nexora` (interface + fonctions), `apps/nexora-mcp`, `scripts/`, CI.

## 1. Synthèse

Le code est **soigné et discipliné là où on le regarde** : validation d'entrée des
fonctions d'écriture sérieuse, 188 tests unitaires, un script d'invariants de dépôt
remarquablement pensé, une gestion correcte du changement d'heure. Le problème n'est pas
la rigueur — c'est **une décision d'architecture qui plafonne tout le reste**.

Les trois constats qui comptent :

1. **L'application transpile 2,49 Mo de JSX dans le navigateur à chaque chargement.**
   Mesuré : **3,78 s de transpilation Babel sur un CPU serveur**, 413 Mo de mémoire, sur
   le fil principal — auxquels s'ajoutent 2,8 Mo de `babel.min.js` à télécharger d'abord.
   Sur mobile, c'est un ordre de grandeur au-dessus.
2. **Quatre origines externes exécutent du code sans aucun contrôle d'intégrité**, et le
   site principal n'a **aucune CSP** — alors que le site MCP, dans le même dépôt, en a une
   complète et correcte. L'asymétrie est le signe d'un oubli, pas d'un arbitrage.
3. **Les couleurs sémantiques échouent au contraste AA** : `--accent` à 2,59:1 est utilisé
   34 fois comme couleur de texte, `--danger` (4,02:1) 49 fois, `--warning` (2,15:1) 5 fois.
   Et **aucune région `aria-live` n'existe** : rien de ce qui change en arrière-plan n'est
   annoncé.

**Risque principal s'il n'est rien fait** : le monofichier de 41 737 lignes rend chaque
correctif plus cher que le précédent, et la transpilation navigateur rend l'application
inutilisable sur un mobile d'entrée de gamme. Ce n'est pas un risque de panne — c'est un
risque d'enlisement : le jour où le chantier du build devient urgent, il sera trop gros.

### Rien à signaler — vérifié, conforme

- **Validation d'entrée des écritures.** `nexora-create-task.ts` plafonne les longueurs,

  sépare proprement erreurs client (400) et serveur (502). C'est du bon travail.
- **`/api/nexora/health` non authentifié** : conforme, `openapi.yaml:15` le déclare

- **Anneau de focus.** `part-003:12791` pose une règle globale `:focus-visible`

- **Changement d'heure.** `schedule: "0 5,6 * * *"` + garde sur l'heure locale de Paris :

- **`ignore` de `netlify.toml`** : la règle `git diff --quiet … -- .` fait bien ce qu'elle

## 3. Fiches détaillées — constats bloquants et majeurs

### Fiche 1 — Transpilation Babel dans le navigateur (bloquant, XL)

**Ce qui se passe.** `part-000` charge `@babel/standalone` depuis unpkg, puis déclare un
unique `<script type="text/babel" data-type="module" data-presets="react">` qui contient
**2 611 801 octets de JSX**. À chaque ouverture de page, le navigateur télécharge 2,8 Mo
de compilateur, puis compile 2,49 Mo de source, sur le fil principal.

**Mesure.** Reproduite avec `@babel/standalone@7.24.7`, mêmes presets, sur le CPU de cet
environnement :

```
JSX à transpiler : 2.49 Mo
Transpilation    : 3.78 s   (Node v22.22.2)
Sortie           : 2.30 Mo
Mémoire RSS pic  : 413 Mo
```

**Pourquoi c'est un problème.** 3,78 s est un **plancher** sur un CPU de serveur, sans
compter le téléchargement ni le parse de `babel.min.js`. Un mobile milieu de gamme est
couramment 4 à 6× plus lent en mono-thread : l'ordre de grandeur attendu est de 15 à 25 s
d'écran figé — le fil principal est bloqué, donc pas d'indicateur de chargement possible.
413 Mo de pic mémoire est par ailleurs au-delà de ce que tolère un onglet mobile
contraint. *(Le multiplicateur mobile est une estimation, pas une mesure : je n'ai pas
d'appareil ici. Le 3,78 s, lui, est mesuré.)*

**Correction proposée.** Introduire une étape de build qui transpile le JSX **avant** le
déploiement, et supprimer `@babel/standalone` du HTML livré. La contrainte de
reproductibilité à l'octet près (`verify-repository.mjs:59`) porte sur
`source/index.html.part-*` → `dist/index.html` : elle reste satisfaite si la transpilation
s'insère **après** la concaténation, en produisant un second artefact vérifié séparément.
C'est la bonne nouvelle : la concaténation et la transpilation sont deux étapes
indépendantes, elles n'ont pas à être fusionnées.

**Ce que ça risque de casser.** Les 9 fichiers de tests extraient leurs blocs de
`dist/index.html` entre sentinelles `// === NEXORA:*:START ===`. Si `dist/index.html`
devient du JS transpilé, les sentinelles survivent (ce sont des commentaires que Babel
conserve par défaut) mais le **code entre elles change de forme**. Il faut soit faire
pointer les tests sur l'artefact intermédiaire non transpilé, soit vérifier que les
sentinelles et le code extrait restent exploitables. À trancher avant d'écrire une ligne.

**Comment le vérifier.** `npm run verify` doit rester vert ; puis mesurer le temps jusqu'au
premier rendu utile avant et après, sur le même appareil, et publier les deux chiffres.

### Fiche 2 — Aucune intégrité sur les dépendances exécutables (majeur, M)

**Ce qui se passe.** Six URL externes sont chargées à l'exécution, dont quatre exécutent du
code :

| Origine | Ce qui est chargé |
|---|---|
| `unpkg.com` | `@babel/standalone@7.24.7/babel.min.js` |
| `esm.sh` | `react@18.2.0`, `react-dom@18.2.0`, `@tabler/icons-react@3.46.0`, `lucide-react@0.383.0`, `papaparse@5.4.1` |
| `www.gstatic.com` | `firebasejs/10.12.2` — app, auth, firestore |
| `fonts.googleapis.com` / `fonts.gstatic.com` | police Inter |

`grep -c 'integrity=' index.html.part-*` renvoie `0` sur les quatre fragments.

**Pourquoi c'est un problème.** Les versions sont épinglées, ce qui est déjà mieux que la
moyenne — mais un épinglage de version n'est pas un épinglage de **contenu**. Si l'une de
ces origines sert un jour autre chose sous la même URL, le code s'exécute dans la page avec
la session Firebase authentifiée de l'utilisateur : lecture et écriture de toutes les
données. Il n'y a pas de second rempart, puisqu'il n'y a pas de CSP (fiche 3).

**Correction proposée.** Ajouter `integrity="sha384-…"` + `crossorigin="anonymous"` sur les
`<script>` et `<link>` chargés par balise. Les imports ESM dynamiques depuis `esm.sh` ne
peuvent pas porter d'attribut `integrity` : ils relèvent de la CSP (fiche 3) ou, mieux, du
même chantier de build que la fiche 1 — une fois les dépendances empaquetées localement, le
problème disparaît entièrement. C'est un argument de plus pour la fiche 1.

**Ce que ça risque de casser.** Une empreinte erronée bloque le chargement complet de
l'application. À valider sur une préproduction, jamais directement.

### Fiche 3 — Pas de CSP sur le site principal (majeur, M)

**Ce qui se passe.** `apps/nexora/public/_headers` **n'existe pas**. `netlify.toml` ne pose
d'en-têtes que sur `/api/*` (`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`).
Le document HTML lui-même est servi sans `Content-Security-Policy`, sans
`X-Frame-Options`, sans `Referrer-Policy`.

Le site MCP, dans le même dépôt, a `apps/nexora-mcp/public/_headers` :

```
Content-Security-Policy: default-src 'self'; connect-src 'self' https://identitytoolkit.googleapis.com; frame-ancestors 'none'; base-uri 'none'; form-action 'self'
X-Frame-Options: DENY
Referrer-Policy: no-referrer
```

**Pourquoi c'est un problème.** L'asymétrie est le constat : quelqu'un a su écrire une CSP
correcte et restrictive pour un site, et ne l'a pas fait pour l'autre — celui qui porte
toutes les données. Sans `frame-ancestors`, `nexora-project.org` est encadrable, donc
exposé au détournement de clic sur des actions destructives. Sans CSP, l'injection
d'attribut de la fiche 7 n'a aucun filet.

**Correction proposée.** Créer `apps/nexora/public/_headers`. La CSP ne peut pas être aussi
stricte que celle du MCP tant que la fiche 1 n'est pas faite (`'unsafe-eval'` est
**requis** par Babel navigateur, et les origines CDN doivent être listées). Une première
version honnête, à durcir après la fiche 1 :

```
/*
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  X-Content-Type-Options: nosniff
  Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://unpkg.com https://esm.sh https://www.gstatic.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; connect-src 'self' https://esm.sh https://*.googleapis.com https://*.firebaseio.com wss://*.firebaseio.com; frame-ancestors 'none'; base-uri 'none'
```

**Ce que ça risque de casser.** Beaucoup, et silencieusement. Une CSP trop stricte casse
Firestore (WebSocket), les imports `esm.sh`, ou les polices. À déployer d'abord en
`Content-Security-Policy-Report-Only`, observer, puis basculer. Les `connect-src` de
Firestore sont notoirement pénibles à cadrer — prévoir une itération.

### Fiche 4 — Contraste des couleurs sémantiques (majeur, S)

**Ce qui se passe.** Le thème effectif est toujours `body[data-life-app="nexora"]`
(`part-000:726`, écrit en dur). Ce thème remappe `--bg`, `--surface`, `--border`,
`--text-*` sur la famille `--life-*` — mais **pas** `--accent`, `--danger`, `--warning`,
`--success`, qui gardent leurs valeurs de base.

Ratios calculés sur les valeurs effectives, sur `--surface` (#ffffff) et `--life-bg`
(#f3f5f9) :

| Token (valeur effective) | Usages en `color:` | sur #ffffff | sur #f3f5f9 | AA 4,5:1 |
|---|---|---|---|---|
| `--warning` #E2A63B | 5 | **2,15** | **1,97** | échec |
| `--accent` #FF7A3D | 34 | **2,59** | **2,37** | échec |
| `--success` #1FA971 | 18 | **3,01** | **2,76** | échec |
| `--danger` #E2483E | 49 | **4,02** | **3,68** | échec |
| `--text-muted` → #66758b | 79 | 4,69 | **4,29** | partiel |
| `--text-secondary` → #53647b | — | 6,04 | 5,53 | OK |
| `--text-primary` → #18263d | — | 15,18 | 13,91 | OK |

**Pourquoi c'est un problème.** Ce ne sont pas des couleurs décoratives : ce sont celles
qui portent l'information de criticité, de retard et d'erreur. `--danger` à 4,02:1 sert
49 fois à dire qu'une tâche est en retard — c'est précisément l'information qui ne doit
pas se perdre. `--warning` à 2,15:1 est illisible pour une bonne part des utilisateurs, y
compris sans déficience visuelle, sur un écran mal calibré ou en plein jour.

Le cas de `--text-muted` est instructif : il passe sur blanc (4,69) et échoue sur le fond
gris (4,29). C'est exactement le genre d'écart qu'un audit global manque et qu'un token
unique par rôle résout.

**Correction proposée.** Assombrir les quatre couleurs sémantiques jusqu'à 4,5:1 sur le
fond le plus clair **et** le plus sombre sur lesquels elles apparaissent, en conservant
leur teinte. Ce sont 4 valeurs hexadécimales à changer — d'où l'effort S. Le vrai travail
est de vérifier qu'aucune n'est utilisée comme couleur de **fond** avec du texte clair
par-dessus, auquel cas il faut une paire (texte / fond) et non une valeur unique.

**Comment le vérifier.** Recalculer les ratios avec le script de cet audit avant / après,
et publier le tableau. C'est objectif et ça prend une minute.

### Fiche 5 — Aucune région `aria-live` (majeur, M)

**Ce qui se passe.** `grep -c aria-live` sur les quatre fragments renvoie **0**.

**Pourquoi c'est un problème.** Nexora est une application où presque tout est asynchrone :
enregistrement d'une tâche, synchronisation Firebase, conflit 409 résolu par fusion, import
CSV, échec réseau. Un utilisateur de lecteur d'écran ne reçoit **aucune** de ces
informations : l'action semble ne rien faire. C'est un échec du critère WCAG 4.1.3
(*Status Messages*), et c'est aussi un problème pour tout le monde — voir la fiche 17.

Le paradoxe vaut d'être noté : le dépôt contient un mécanisme de fusion de conflits de
synchronisation soigné, testé, commenté sur plusieurs paragraphes
(`verify-repository.mjs`, `sync-merge.test.mjs`) — et son résultat n'est jamais annoncé.

**Correction proposée.** Une seule région `aria-live="polite"` montée une fois à la racine,
alimentée par le mécanisme de notification existant, suffit pour l'essentiel. Ajouter
`aria-live="assertive"` uniquement pour les erreurs bloquantes. Ne pas multiplier les
régions : plusieurs régions concurrentes se parasitent.

### Fiche 6 — Rapports planifiés annulés en silence (majeur, S)

**Ce qui se passe.**

```ts
// nexora-report-morning-scheduled.ts:9
if (local.hour !== 7 || local.minute !== 0) return;
// nexora-report-evening-scheduled.ts:9
if (local.hour !== 20 || local.minute !== 30) return;
```

La double programmation (`0 5,6 * * *`) est **correcte** : elle absorbe le changement
d'heure, l'une des deux invocations tombe sur 7 h de Paris et l'autre est écartée. Le
problème est ailleurs : le test sur la **minute**.

**Pourquoi c'est un problème.** Netlify ne garantit pas la minute exacte de déclenchement
d'une fonction planifiée. Un décalage d'une minute — file d'attente, démarrage à froid —
fait tomber les **deux** invocations dans le `return`. Aucun rapport n'est produit, aucune
exception n'est levée, aucune ligne de journal n'est écrite. L'échec est parfaitement
invisible : personne ne saura jamais qu'il manque le rapport du mardi.

*Je n'ai pas observé de décalage réel — je n'ai pas accès aux journaux Netlify. Le constat
porte sur la construction du garde, qui transforme un retard bénin en perte silencieuse.*

**Correction proposée.** Remplacer l'égalité stricte par une fenêtre, et rendre le rejet
audible :

```ts
const cible = 7 * 60;                                   // 07:00 Paris
const ecart = Math.abs(local.hour * 60 + local.minute - cible);
if (ecart > 20) { console.log(`report:skip h=${local.hour}:${local.minute}`); return; }
```

Une fenêtre de ±20 min ne peut pas faire tomber les deux invocations ensemble : elles sont
séparées d'une heure. Le `console.log` rend le saut visible dans les journaux Netlify.

**Comment le vérifier.** Test unitaire sur la fonction de décision, aux quatre instants qui
comptent : les deux invocations en heure d'hiver, les deux en heure d'été, plus un décalage
de 1 et de 25 minutes sur chacune.

### Fiche 7 — Injection d'attribut dans le rendu Markdown (majeur, S)

**Ce qui se passe.** `part-000:1496` :

```js
const escapeHtml = (s) => s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");
```

Ni `"` ni `'` ne sont échappés. Et `part-000:1517` interpole l'URL dans un attribut entre
guillemets :

```js
.replace(/\[(.+?)\]\((https?:\/\/[^\s)]+)\)/g, '<a href="$2" target="_blank" rel="noopener">$1</a>')
```

La classe `[^\s)]+` accepte `"`. Le résultat est passé à `dangerouslySetInnerHTML` en
5 endroits (`part-002:7092`, `part-002:7853`, `part-003:1708`, `part-003:4252`,
`part-003:4530`).

**Reproduit** :

| Entrée (description de tâche) | Sortie |
|---|---|
| `[c](https://x"onmouseover=alert)` | `<a href="https://x"onmouseover=alert" target="_blank" …>` |
| `[c](https://x"style=position:fixed;inset:0;z-index:9999)` | `<a href="https://x"style=position:fixed;inset:0;z-index:9999" …>` |

Les navigateurs tolèrent l'absence d'espace après une valeur d'attribut entre guillemets et
traitent la suite comme un nouvel attribut.

**Portée honnête.** L'**injection d'attribut est confirmée**. Je **n'ai pas démontré
d'exécution de script** : la classe `[^\s)]+` interdit les espaces et les parenthèses
fermantes, et la substitution du code `` ` `` s'applique avant celle des liens, ce qui
retire les deux tournures habituelles (`alert(1)` et ``alert`1` ``). Je ne conclus pas pour
autant qu'elle est impossible — l'absence de preuve d'exploitation n'est pas une preuve
d'absence, et le deuxième exemple montre déjà qu'on peut recouvrir l'écran. `javascript:`
est bien bloqué par le préfixe imposé.

**Correction proposée.** Une ligne :

```js
const escapeHtml = (s) => s.replace(/&/g,"&amp;").replace(/</g,"&lt;").replace(/>/g,"&gt;")
                           .replace(/"/g,"&quot;").replace(/'/g,"&#39;");
```

**Ce que ça risque de casser.** Les guillemets deviennent `&quot;` dans le HTML produit —
invisible à l'affichage. À vérifier : les callouts, qui composent des attributs `style`
depuis la palette fixe (`part-000:1558`), ne sont pas concernés puisque leurs valeurs ne
viennent pas de l'utilisateur.

---

### Fiche 8 — Modales non exposées comme dialogues (majeur, M)

**Ce qui se passe.** 24 composants de type modale
(`TaskModal`, `FiltersModal`, `ImportCsvModal`, `SettingsModal`, `ConfirmModal`, …) pour
**2** occurrences de `role="dialog"` et **2** de `aria-modal`.

**Pourquoi c'est un problème.** Sans `role="dialog"` + `aria-modal="true"`, un lecteur
d'écran ne signale pas l'ouverture, ne restreint pas la navigation au contenu de la modale,
et laisse l'utilisateur parcourir la page derrière. Les 13 gestionnaires `Escape` relevés
montrent que la question de la fermeture a été traitée — c'est le **piège du focus** qui
manque, et la fermeture sans piège de focus donne une fausse impression de complétude.

**Correction proposée.** Un composant `Modal` unique portant `role="dialog"`,
`aria-modal="true"`, `aria-labelledby` vers son titre, le piège du focus et la restitution
du focus à la fermeture — puis migration des 24 composants dessus. C'est le chantier qui
sert le plus l'accessibilité **et** la cohérence (fiche 10) en une fois.

---

### Fiche 9 — Le monofichier (majeur, XL)

**Ce qui se passe.** `source/index.html.part-000..004` reconstruit un fichier de
**41 737 lignes / 2,80 Mo** contenant 189 composants React, 530 `useState`, 251 `useMemo`,
5 blocs `<style>` et toute la logique métier.

**Pourquoi c'est un problème — et pourquoi ce n'est pas si simple.** Le coût est réel :
aucun outil de revue n'affiche un diff utile là-dedans, tout conflit de fusion est manuel,
et la découpe en fragments de ~700 Ko est arbitraire — une fonction peut être coupée en
deux au milieu, ce qui rend `grep` trompeur (j'ai buté dessus pendant cet audit).

Mais le dépôt a construit **des contre-mesures qui fonctionnent** : les sentinelles
`// === NEXORA:*:START ===` délimitent des blocs de logique pure extractibles et testables,
et `verify-repository.mjs` (525 lignes) vérifie par correspondance de motifs des invariants
qu'aucun compilateur n'attraperait — un onglet de réglages sans volet rendu, un hook placé
après un retour conditionnel, une capsule de criticité supprimée sur deux. Les commentaires
expliquent pour chaque garde le bug réel qu'il a attrapé. C'est inhabituellement lucide.

Le diagnostic n'est donc pas « c'est mal fait » mais : **ces contre-mesures sont le prix
payé pour l'architecture, et ce prix augmente.** `verify-repository.mjs` est lui-même
devenu un fichier de 525 lignes de motifs fragiles qu'il faut maintenir.

**Correction proposée.** Ne pas découper pour découper. Le découpage n'a de valeur que
s'il vient **avec** la fiche 1 : une fois qu'il existe une étape de build, extraire des
modules devient possible sans rien perdre. Découper avant, c'est ajouter de la complexité
sans bénéfice. **Cette fiche est une conséquence de la fiche 1, pas un chantier séparé.**

---

### Fiche 10 — Dix-huit points de rupture (majeur, M)

**Ce qui se passe.** 16 valeurs `max-width` distinctes, plus `hover:none` et `print` :

```
520  600  640  650  680  700  720  760  767  800  820  880  900  980  1023  1100
```

**Pourquoi c'est un problème.** Entre 700 et 767 px il y a **quatre** points de rupture
(700, 720, 760, 767). Une tablette en portrait traverse les quatre en quelques pixels de
redimensionnement, et chaque passage réarrange une partie de l'interface indépendamment des
autres. Le résultat est une mise en page qui ne bascule jamais d'un bloc : elle se
décompose par morceaux. C'est aussi impossible à tester — il faudrait 16 largeurs de
référence.

**Correction proposée.** Trois ou quatre points de rupture, déclarés comme tokens
(`--bp-mobile: 640px`, `--bp-tablet: 1024px`, `--bp-wide: 1280px`), et migration des 16
valeurs vers le point le plus proche. Migration mécanique mais à faire vue par vue : un
`760` devenu `640` peut casser une grille. Traiter d'abord le groupe 700–767, qui concentre
le désordre et le gain.

---

### Fiche 11 — 568 boutons, 19 `aria-label` (majeur, M)

**Ce qui se passe.** 568 balises `<button>` ouvrantes ; 19 `aria-label` et 414 `title=`
dans l'ensemble du fichier.

**Limite de la mesure, assumée.** Je n'ai **pas** pu établir de façon fiable combien de
boutons donnés sont sans nom accessible. Une expression régulière sur `<button …>` s'arrête
au premier `>`, qui tombe le plus souvent dans une fonction fléchée `onClick={() => …}` :
toute statistique par bouton qui en découlerait serait fausse. Le rapport de 19 `aria-label`
pour 568 boutons reste, lui, solide, et il suffit à établir le constat.

`title` n'est par ailleurs pas un substitut : il n'est pas restitué au toucher, ni de façon
fiable par tous les lecteurs d'écran.

**Correction proposée.** Recenser les boutons dont le contenu est une icône seule avec
l'outil `tools/visual-check` ou un `axe-core` sur la page rendue — un audit sur le DOM
construit, là où l'analyse statique échoue. Puis ajouter `aria-label` en même temps que la
migration de la fiche 8, qui touche déjà ces zones.

## 5. Chantiers de fond

### A — Sortir Babel du navigateur (fiches 1, 2, 9)

Le chantier structurant. Découpé pour être livrable par étapes :

1. **Décider du sort des tests.** Les 9 fichiers extraient du code de `dist/index.html`.
   Choisir : tests sur l'artefact intermédiaire, ou sentinelles préservées à la
   transpilation. *Rien ne commence avant cette décision.* (½ journée d'analyse)
2. **Étape de transpilation hors ligne** après la concaténation, produisant un second
   artefact. `verify-repository.mjs` continue de vérifier la concaténation ; une nouvelle
   garde vérifie la transpilation. (1–2 jours)
3. **Empaqueter les dépendances `esm.sh` localement** — ce qui règle la fiche 2 par
   disparition du problème plutôt que par contournement. (1 jour)
4. **Retirer `@babel/standalone`** du HTML livré et mesurer. (½ journée)
5. **Durcir la CSP** une fois `'unsafe-eval'` devenu inutile. (½ journée)
6. **Alors seulement**, envisager la découpe en modules (fiche 9), devenue possible sans
   perte.

Chaque étape est déployable seule. Les étapes 1 à 3 ne changent **rien** pour
l'utilisateur : elles peuvent s'accumuler sur la branche sans urgence de publication.

### B — Socle d'accessibilité (fiches 5, 8, 11)

1. Une région `aria-live` unique branchée sur les notifications existantes. (1 jour)
2. Un composant `Modal` de référence — `role`, `aria-modal`, piège et restitution du focus.
   (1–2 jours)
3. Migration des 24 modales dessus, par lots de 5 ou 6, en ajoutant au passage les
   `aria-label` des boutons icône-seule rencontrés. (3–4 jours, fractionnables)

### C — Unification du design system (fiches 10, 12)

1. Réduire à 3–4 points de rupture, en commençant par le groupe 700–767. (1–2 jours)
2. Migrer les 589 hexadécimaux vers des tokens, **fichier par fichier**, en commençant par
   les 10 valeurs les plus répétées (`#64748b` 28×, `#ff7a3d` 23×, `#94a3b8` 19×) qui
   couvrent à elles seules une bonne part du total. (itératif, sans fin imposée)

### D — Tests d'interface (fiche 16)

Les 188 tests existants couvrent la logique pure, correctement. Le maillon manquant est le
rendu. `tools/visual-check` existe déjà dans le dépôt : le chantier est d'en faire une
étape de CI plutôt que de repartir de zéro. À cadrer après le chantier A, qui changera la
façon dont la page se construit.

## 7. Hors périmètre / non vérifié

Cette section est la plus importante à lire avant d'agir sur ce rapport.

- **Aucune exécution réelle de l'interface.** Pas de navigateur lancé, pas de capture, pas
  de parcours effectué. Tout l'axe UI/UX repose sur l'analyse statique du source. En
  conséquence, **les rubriques 2 (hiérarchie et densité), 5 (états), 6 (parcours clés),
  7 (mobile) et 9 (micro-interactions) de la grille UI/UX ne sont pas traitées** — elles
  exigent de voir l'application. Ce qui figure ci-dessus pour ces rubriques (fiche 17) est
  ce que le comptage permet de dire, pas un jugement d'usage.
- **Aucune mesure de performance réelle.** Le 3,78 s est mesuré sur un CPU serveur en Node,
  hors navigateur, hors réseau. Le premier rendu utile en conditions réelles n'est pas
  mesuré. Le multiplicateur mobile est une estimation explicitement étiquetée comme telle.
- **Nom accessible par bouton : non mesurable statiquement.** Voir la fiche 11. Le constat
  global tient ; sa ventilation exigerait un audit sur le DOM rendu.
- **Aucune exécution de script démontrée** pour la fiche 7. L'injection d'attribut est
  confirmée, l'escalade ne l'est pas. Corriger quand même.
- **Règles de sécurité Firebase non auditées.** Elles ne sont pas dans le dépôt — c'est
  conforme à la politique de garde-fous, mais cela signifie que la couche qui décide
  réellement qui lit et écrit quoi **n'a pas été vue**. C'est le plus grand angle mort de
  cet audit. À traiter dans la console Firebase.
- **Journaux Netlify non consultés** : fréquence réelle des rapports manquants (fiche 6),
  taux d'erreur des fonctions, temps de réponse. Inconnu.
- **`apps/nexora-mcp` audité en surface.** La chaîne OAuth, les 4 fichiers source et les
  6 fichiers de tests n'ont pas été lus ligne à ligne. La zone `zone:mcp` n'est pas couverte
  et mériterait sa propre passe.
- **Rédaction d'interface (rubrique 8) non traitée** : juger des libellés hors de leur
  contexte d'affichage produit des remarques sans valeur.
- **`tools/visual-check` non exécuté.** Il existe et pourrait être l'outil manquant pour
  lever plusieurs des limites ci-dessus.
